# Подробное руководство

Здесь собрано всё, что не вошло в короткий README: устройство, безопасность, порты и тома,
простой режим, переход со старой установки, администрирование серверов и правила.

Адреса в примерах — заглушки: `<NL_IP>`, `<USA1_IP>`, `<USA2_IP>`, `<адрес-репозитория>`, `<имя>`.
Подставьте свои значения.

## 1. Как устроено

Схема:

```
ваши программы → 127.0.0.1:7890 (контейнер proxy) → сервер NL → сервер USA
```

Панель (браузер) работает с контейнером `kit`. Контейнер `proxy` пропускает трафик.

Почему два контейнера:
- `kit` хранит ключ, базу и токен входа. Он не передаёт трафик.
- `proxy` передаёт трафик. У него нет ключа, базы и токена. Если с ним что-то случится, секреты не утекут.
- Оба контейнера собраны из одного образа, но запускаются с разными правами и разными томами.

Оба порта опубликованы только на `127.0.0.1`, то есть только на этом компьютере:
- `4050` — панель в браузере;
- `7890` — прокси для ваших программ (HTTP и SOCKS5).

Docker-сокет (доступ контейнера к Docker самого компьютера) не монтируется.

## 2. Безопасность простыми словами

- Панель открывается только по ссылке с токеном. Токен хранится в томе `kit-data` (файл `ui-token`).
  Ссылку можно заново получить командой `docker compose exec kit kit token`.
- Кто может запускать Docker на вашем компьютере, может прочитать токен. Это принятое ограничение.
- SSH-ключ к серверу монтируется в контейнер только для чтения. Он не попадает в образ, базу или ответы панели.
- Ключ сервера NL проверяется: отпечаток нужно подтвердить вручную. Так панель не подключится к чужому серверу
  по ошибке. Файл с подтверждёнными ключами — `known_hosts` в томе `kit-data`.
- Ссылки `vless://` — это ключи доступа. Они видны только через ссылки сервера в панели, в журналах их нет.
- Контейнеры работают без лишних прав, с файловой системой только для чтения.
- `kit` и `proxy` видят тома друг друга только на чтение: `kit` не пишет в `kit-state`, `proxy` не пишет в `kit-gen`.

Что не защищено:
- Если токен попал к посторонним, закройте доступ: `docker compose down -v` и заново создайте ключи и ссылки.
- Если кто-то получил доступ к Docker, он получил доступ ко всему. Это граница Docker, а не панели.

## 3. Порты и тома

| Что | Где | Зачем |
|---|---|---|
| Панель | `127.0.0.1:4050` | браузер |
| Прокси | `127.0.0.1:7890` | ваши программы |
| Том `kit-data` | контейнер `kit` | база, токен, подтверждённые ключи (`known_hosts`) |
| Том `kit-gen` | `kit` пишет, `proxy` читает | конфигурации Xray и Mihomo |
| Том `kit-state` | `proxy` пишет, `kit` читает | статус и журналы прокси, домашний каталог Mihomo |

Порт меняется в `.env`: `KIT_UI_PORT` для панели, `KIT_PROXY_PORT` для прокси. После изменения выполните `docker compose up -d`.

Удаление томов: `docker compose down` оставляет тома, `docker compose down -v` удаляет их вместе с базой.

## 4. Режим импорта ссылок

Этот режим нужен, если у вас нет доступа к серверу и ключа. Владелец даёт ссылки `vless://`.

Как устроена ссылка. Она создаётся кнопкой «Показать ссылки» на панели владельца. В подписи (после `#`)
стоит IP выхода и тип входа, например `NL -> <USA2_IP> TCP ...`. По этой подписи панель понимает, куда ведёт вход.

Что проверяет импорт:
- все поля ссылки по строгим правилам (uuid, ключи, порт, тип, параметры);
- подпись с IP выхода и типом, совпадающим с параметрами ссылки;
- не больше 40 ссылок за раз и не больше 1024 символов в каждой.

Если хотя бы одна ссылка неверна, не сохраняется ничего. Панель показывает номер строки и причину.
Новый импорт заменяет старый список импортированных входов. Если ссылка совпадает по порту и uuid с входом, обнаруженным через NL, импорт перекрывает этот вход. Остальные обнаруженные входы не трогаются.

Что видно в панели: импортированные входы помечены значком «импорт».

Порт 443 не устанавливается этим установщиком: такие ссылки отклоняются.

Важно: импортированная ссылка — это клиент вашего сервера. Она не даёт доступа к серверу NL,
к его панели 3x-ui или по ssh. Отключить ссылку может только владелец, удалив или заменив uuid клиента на сервере.

## 5. Переход со старой установки на хосте

Старая установка ставила Mihomo и Xray прямо в систему, через systemd (Linux) или LaunchAgent (macOS).
Она занимает порт `7890`, поэтому её нужно выключить до первого запуска панели.
Проект сам ничего не останавливает.

Linux и WSL:

```bash
systemctl --user disable --now mihomo.service xray-mihomo.service xhttp-nl-admin-tunnel.service 2>/dev/null || true
crontab -l 2>/dev/null | grep -n mihomo || true   # строки mihomo-keepalive удалите вручную: crontab -e
ss -ltnp 'sport = :7890'                          # должно быть пусто
```

macOS:

```bash
for L in com.mihomo.proxy com.mihomo.xray; do
  launchctl bootout "gui/$(id -u)/$L" 2>/dev/null || true
  launchctl disable "gui/$(id -u)/$L"
done
lsof -nP -iTCP:7890 -sTCP:LISTEN                  # должно быть пусто
```

Старые файлы можно удалить вручную. Проект их не трогает:
`~/.local/bin/{mihomo,xray}`, `~/.config/mihomo/`,
`~/.config/systemd/user/{mihomo,xray-mihomo,xhttp-nl-admin-tunnel}.service`,
`~/Library/LaunchAgents/com.mihomo.{proxy,xray}.plist`.

Строки `http_proxy` в оболочке (`~/.bashrc`, `~/.zshrc`) продолжают работать: они указывают на `127.0.0.1:7890`.

Если панель показывает «Прокси-контейнер не работает», порт 7890 почти наверняка занят старой установкой.
Выполните команды выше и затем `docker compose up -d`.

### Обновление с тома kit-run на два тома

Раньше оба контейнера писали в один том `kit-run`. Теперь это два тома: `kit-gen` и `kit-state`.
Данные в `kit-run` можно пересоздать, поэтому миграция простая:

1. Остановите стек без `-v`: `docker compose down`. Флаг `-v` удалит `kit-data` (базу, токен, known_hosts).
2. Запустите стек: `docker compose up -d --build`. Появятся тома `mihomo-proxy-kit_kit-gen` и `mihomo-proxy-kit_kit-state`.
3. В панели снова нажмите «Установить» для входа, который был активен. До этого прокси в состоянии `idle`,
   порт 7890 закрыт. База, правила, токен и ключи хоста сохраняются.
4. Удалите старый том: `docker volume rm mihomo-proxy-kit_kit-run`.
   Если проект запускался с `-p <имя>`, том называется `<имя>_kit-run`.

## 6. Администрирование серверов

Это для владельца сервера, не для клиента. Клиенту эти команды не нужны.

Команды ходят по ssh на NL, USA1 и USA2. Адреса берутся из файла `proxy.env`, который не попадает в git:

```bash
SERVER_IP=<NL_IP>
SSH_TUNNEL_NL=root@<NL_IP>
SSH_TUNNEL_SERVER=root@<USA1_IP>
SSH_TUNNEL_SERVER_2=root@<USA2_IP>
```

Пример файла лежит в `proxy.env.example`. Значения в него вписывайте сами.

Команды:
- `./proxy server status` — версия Xray и состояние службы на серверах.
- `./proxy server logs [nl|usa1|usa2|all] [-n N]` — журналы служб серверов.
- `./proxy server update ВЕРСИЯ [nl|usa1|usa2|all] [--yes]` — обновить Xray по одному серверу.
  После каждого сервера проверка. Если проверка не прошла, сервер откатывается, обновление останавливается.
  Без `--yes` команда спрашивает подтверждение. Эта команда ещё не запускалась на реальных серверах:
  сначала проверьте её на одном USA.

Первичная настройка нового сервера: `bash server/setup-server.sh` (запускать на сервере).

## 7. Правила подробно

Вкладка «Правила». Типы правил:
- `DOMAIN` — точное имя сайта, например `example.com`;
- `DOMAIN-SUFFIX` — сайт и все его поддомены;
- `DOMAIN-KEYWORD` — слово в имени сайта;
- `GEOSITE` — готовая группа сайтов (например, российские);
- `GEOIP` — страна по IP-адресу (например, `RU`);
- `IP-CIDR` — диапазон IP-адресов.

Политики:
- `PROXY` — через сервер;
- `DIRECT` — напрямую, с вашего IP;
- `REJECT` — не открывать.

`MATCH` — политика для всего, что не подошло ни под одно правило. Правила проверяются сверху вниз, первое совпадение побеждает.

Служебное правило `DOMAIN,api.ipify.org,PROXY` всегда первое и не редактируется. Оно нужно для проверки выхода.

По умолчанию через `PROXY` идут ChatGPT, Claude и Telegram. Российские домены, локальные адреса и `GEOIP,RU` идут напрямую.
Кнопка «Сохранить и применить» пересоздаёт конфигурацию Mihomo.

## 8. Программы и системный прокси

Программы должны знать адрес прокси:
- HTTP: `http://127.0.0.1:7890`;
- SOCKS5: `socks5://127.0.0.1:7890`.

Для терминала проще всего команда проекта (работает только на этом компьютере, без Docker и без ssh):

```bash
./proxy env on           # добавить блок в ~/.bashrc (или ~/.zshrc для zsh)
source ~/.bashrc         # применить в текущем окне, или откройте новое окно
./proxy env off          # удалить блок
./proxy env status       # проверить, есть ли блок
```

Блок ограничен строками `# >>> mihomo-proxy-kit >>>` и `# <<< mihomo-proxy-kit <<<`. Команда не трогает строки вне блока,
сохраняет права файла и отказывается работать, если файл оболочки — символическая ссылка.
Порт по умолчанию 7890; другой порт: `./proxy env on --port 7891`. Выбрать файл вручную: `--shell bash` или `--shell zsh`.

Контейнеры не пишут в файлы оболочки: эту команду запускает владелец сам.

Вручную, если нужно, то же самое:

```bash
export http_proxy=http://127.0.0.1:7890
export https_proxy=http://127.0.0.1:7890
export all_proxy=socks5://127.0.0.1:7890
```

Для Claude Code, Codex и других консольных инструментов: `bash setup-ai-cli-proxy.sh`.
Прокси контейнера должен работать. Скрипт читает только переменные окружения, файл `proxy.env` не читает.

Системный прокси macOS проект не настраивает. Это делается вручную, `Wi-Fi` замените на своё имя сети:

```bash
networksetup -setwebproxy "Wi-Fi" 127.0.0.1 7890
networksetup -setsecurewebproxy "Wi-Fi" 127.0.0.1 7890
networksetup -setsocksfirewallproxy "Wi-Fi" 127.0.0.1 7890
# выключить:
networksetup -setwebproxystate "Wi-Fi" off
networksetup -setsecurewebproxystate "Wi-Fi" off
networksetup -setsocksfirewallproxystate "Wi-Fi" off
```

В WSL программы Windows достигают `127.0.0.1:7890` через переадресацию localhost (включена по умолчанию).

Ограничения:
- UDP через опубликованный порт не работает: только TCP (HTTP и SOCKS5 CONNECT).

## 9. Известные риски

- Вход в панель защищён токеном в ссылке, а не отдельным логином. Это сознательное упрощение для одного пользователя.
- `proxy` может подменить только свой том `kit-state`: статус и журналы. Конфигурации он прочитать может, но не изменить.
- Том `kit-state` не ограничен по размеру. Журналы ротируются, но заполнить диск через прокси теоретически можно.

## 10. Команда proxy из любой папки

Один раз, из папки проекта, создайте ссылку в `~/.local/bin`:

```bash
bash install-cli.sh
```

Скрипт создаёт `~/.local/bin/proxy`, которая указывает на `proxy` в папке проекта. Повторный запуск ничего не меняет.
Если файл `~/.local/bin/proxy` уже есть и это не ссылка на этот проект, скрипт ничего не перезаписывает и говорит, что это.

Если `~/.local/bin` не в `PATH`, скрипт печатает строку, которую нужно добавить вручную в `~/.bashrc` или `~/.zshrc`:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

Скрипт сам файлы оболочки не меняет. После изменения откройте новое окно терминала.

Удалить ссылку, но только свою:

```bash
bash install-cli.sh --remove
```

Скрипт только на хосте: без Docker и без ssh. Команда `proxy` сама находит папку проекта по настоящему пути файла,
поэтому работает из любой папки и через ссылку.
